1. `/vpc` で起動
2. 対話的にテンプレートの各セクションを埋めていく
3. 完成したドキュメントを指定パスに保存

## 作成フロー

1. ユーザーに保存先パスを確認する
2. `${CLAUDE_PLUGIN_ROOT}/skills/vpc/references/template.md` を読み込む
3. テンプレートの各セクションについて、ユーザーと対話しながら内容を埋める
   - 既存の関連ドキュメント（リーンキャンバス、インタビュー結果等）があれば参照する
   - 不明な箇所は仮説として「💡」ラベルを付ける
4. 完成したドキュメントを保存先パスに書き出す
5. 実例との比較確認を提案する（`${CLAUDE_PLUGIN_ROOT}/skills/vpc/examples/example.md`）

# VPC ガイド

## このガイドについて

VPC（Value Proposition Canvas）の書き方・使い方を解説する。テンプレートは [template.md](template.md) を使用。

## VPCとは

カスタマープロフィール（右側）とバリューマップ（左側）の2つで構成され、ユーザーの課題とプロダクトの価値提案の**Fit（適合）**を確認するフレームワーク。

```
バリューマップ（左側）          カスタマープロフィール（右側）
┌─────────────────────┐    ┌─────────────────────┐
│ Gain Creators       │    │ Gains               │
│ (ゲインをつくる)     │    │ (得たい成果)         │
│                     │    │                     │
│ Products & Services │    │ Customer Jobs       │
│ (機能・仕組み)      │←Fit→│ (達成したいタスク)   │
│                     │    │                     │
│ Pain Relievers      │    │ Pains               │
│ (ペインを取り除く)   │    │ (障害・不安)         │
└─────────────────────┘    └─────────────────────┘
```

**目的**: ユーザーが本当に求めていることと、プロダクトが提供する価値の整合性を可視化する
**インプット**: Core定義（ビジョン）、市場・競合調査
**アウトプット**: カスタマープロフィール + バリューマップ + 検証ポイント

## ディスカバリーワークフローにおける位置づけ

```
Core定義（ビジョン・ミッション）
  ↓
Why定義 ユーザー側
  ├─ 【VPC作成】◀ ここ
  ├─  仮説立案（VPCから仮説を抽出・構造化）
  ├─  インタビュー（仮説を検証）
  ├─  KJ法分析（結果を構造化）
  └─  VPC更新（検証結果を反映）
```

## 記入順序

**右側（カスタマープロフィール）から先に書く。**

1. **Customer Jobs**: ユーザーが達成したいタスク・仕事
2. **Pains**: それを妨げている障害・不安
3. **Gains**: 達成できたときに得たい成果
4. **Pain Relievers**: ペインをどう取り除くか
5. **Gain Creators**: ゲインをどう実現するか
6. **Products & Services**: 具体的な機能・仕組み

> 左側（バリューマップ）は右側の裏返しではない。根本原因を分析した上で、構造的な解決策を設計する。

## 4段階アプローチ（肉厚なVPCの作り方）

各Pains/Gainsを表面的な記述で終わらせず、4段階で深掘りすることで「肉厚な」VPCを実現する。

```
事実（What）    → ユーザーに実際に起きていること
    ↓
分析（Why）     → なぜそのペインが発生するか（根本原因）
    ↓
戦略（How）     → どうアプローチするか（方針）
    ↓
提案（Value）   → 具体的な価値提案（差別化された解決策）
```

### 例：「外部から見た自分の市場価値がわからない」というペイン

| 段階 | 内容 |
|------|------|
| **事実** | 外部からの市場価値がわからない |
| **分析** | 評価基準が異なる（SIer=「プロジェクトを回せるか」、事業会社=「技術で課題を解決できるか」） |
| **戦略** | 評価軸の違いそのものを可視化する |
| **提案** | 「SIer→事業会社 評価軸変換マップ」機能 |

> 単なるペインの裏返し（「金額が高い」→「低価格」）を避け、根本原因に基づいた説得力のある価値提案につなげる。

## 仮説と事実の区別

VPCの各項目には 💡（仮説）と 📘（事実）のラベルを付ける。

- 💡マークがついた項目 = 検証が必要
- 📘マークがついた項目 = データや調査で裏付け済み

検証後は 📗（検証済み・支持）または ❌（棄却）に更新する。

## 検証ポイントの設計

VPC作成後、💡マークの仮説を検証ポイントとして定義する。

各検証ポイントには以下を設定：
- **検証すべき仮説**: 何を確かめたいか
- **対応設問**: インタビュースクリプトのどの質問で検証するか（Q2, Q3等）
- **検証方法**: インタビュー / デスクリサーチ / プロトタイプテスト
- **判定基準**: 何名中何名が言及したら支持とするか

### 検証ポイントの粒度

| 粒度 | 例 | 検証方法 |
|------|-----|---------|
| ペイン・ゲイン仮説 | 「ターゲット層は〇〇に困っている」 | インタビュー |
| ソリューション仮説 | 「この機能で課題が解決される」 | プロトタイプテスト |
| 前提条件 | 「ターゲット層は〇〇というセグメントに存在する」 | デスクリサーチ |

## Fit確認のポイント

左右の整合性を確認する際のチェック項目：

- [ ] 各Painに対応するPain Relieverがあるか？
- [ ] 各Gainに対応するGain Creatorがあるか？
- [ ] Products & Servicesが具体的な価値提案に紐づいているか？
- [ ] Customer Jobsのフェーズごとにペイン・ゲインが網羅されているか？
- [ ] 事実と仮説が明確に区別されているか？
- [ ] 上位層（Core ビジョン）と矛盾していないか？
