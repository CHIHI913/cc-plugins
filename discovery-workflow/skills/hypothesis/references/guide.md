# 仮説立案 ガイド

## このガイドについて

仮説の立て方・構造化・検証設計の方法を解説する。テンプレートは [template.md](template.md) を使用。

## 仮説立案とは

VPCのカスタマープロフィールから仮説を抽出し、検証可能な形に構造化するステップ。思い込みと事実を分離し、検証すべき仮説を優先順位付きで可視化する。

**インプット**: VPC（カスタマープロフィール + バリューマップ）
**アウトプット**: 仮説一覧 + 検証ポイント定義

## 仮説のミルフィーユ（4層構造）

仮説は4つの階層に分かれる。上位の仮説ほど抽象的で影響範囲が大きく、下位ほど具体的。**上位の仮説を間違えると、下位の仮説がすべて崩れる**。

```
Core（最も抽象的・影響大）
│  「プロダクトが実現したい世界観」
│    例: 「誰もが自分に合ったキャリアを選べる世界」
↓
Why（価値層）
│  「ユーザーがどんな状態になっているか」
│    例: 「キャリアの方向性に確信をもって転職活動ができる」
↓
What（体験層）
│  「ユーザーが体験するソリューション」
│    例: 「AIがキャリア戦略を提案してくれる」
↓
How（最も具体的・影響小）
   「機能実装・UIデザインの詳細」
     例: 「チャット形式で質問に答えるとキャリア診断が出る」
```

**検証の方向**:
- **上→下（「なぜ？」）**: 上位の仮説が正しいなら、下位の仮説は妥当か？
- **下→上（「だから何？」）**: この機能が実現されると、本当にユーザーの課題が解決されるか？

> 仮説立案の段階では、まずWhy層（カスタマープロフィール系）の仮説を固めることが最優先。

## 仮説と事実の区別

記述する際、仮説と事実を明確に区別する。

| ラベル | 意味 | 例 |
|--------|------|-----|
| 事実 | データ・調査・実績で裏付けられている | 「転職者の70%がエージェント経由（doda調査）」 |
| 💡 仮説 | まだ検証されていない推測 | 「💡 ユーザーはキャリアの方向性に不安を感じている」 |

> VPCの各項目（Jobs/Pains/Gains）を記述する際、💡マークで仮説を明示する。事実と仮説が混在すると、何を検証すべきかが曖昧になる。

## 仮説の深掘り：4段階アプローチ

VPCのPains/Gainsをより「肉厚」にするために、各仮説を4段階で深掘りする。

```
事実（ユーザーのペイン）
    ↓
分析（なぜそのペインが発生するか）
    ↓
戦略（どうアプローチするか）
    ↓
提案（具体的な価値提案）
```

**例**: 「金額が高い」というペイン
- **事実**: ユーザーが「料金が高い」と感じている
- **分析**: 好みに合わない選択肢も含まれており、コスパが悪いと感じている
- **戦略**: 好みに合わせた選択の手間を軽減し、満足度を高める
- **提案**: 注文履歴に基づく最適な提案機能

> この4段階アプローチにより、表面的な課題の裏にある構造的な問題を特定し、より的確なソリューションにつなげることができる。

## カテゴリ体系

仮説をカテゴリ分けし、IDを付与して管理する。

| カテゴリ記号 | カテゴリ名 | 説明 | 仮説の階層 |
|:---:|------|------|:---:|
| A | カスタマープロフィール | ユーザーのJobs/Pains/Gainsに関する仮説 | Why |
| B | 戦略・ポジショニング | 市場・競合・差別化に関する仮説 | Why |
| C | ソリューション | 解決策・機能に関する仮説 | What |
| D | プロダクト設計 | UX・技術・実装に関する仮説 | How |

カテゴリはプロジェクトに応じて追加・変更してよい。例えば「E: 新発見」（インタビューで発見した想定外の知見）など。

## 優先度の判断基準

```
                高インパクト
                    │
        ┌───────────┼───────────┐
        │  優先度:高 │  優先度:中 │
        │ (確信度低  │ (確信度高  │
        │  影響大)   │  影響大)   │
        │           │           │
高不確実性──────────┼──────────低不確実性
        │           │           │
        │  優先度:中 │  優先度:低 │
        │ (確信度低  │ (確信度高  │
        │  影響小)   │  影響小)   │
        └───────────┼───────────┘
                    │
                低インパクト
```

**優先度:高** = 確信度が低い（不確実）のにビジネスインパクトが大きい仮説。これを間違えると全体が崩れるため、最優先で検証する。

## 検証方法の種類

| 検証方法 | 適する仮説タイプ | 具体例 |
|---------|---------------|--------|
| ユーザーインタビュー | カスタマープロフィール系 | 課題の存在確認、ペインの深さ |
| デスクリサーチ | 市場・競合系 | 市場規模、競合動向 |
| プロトタイプテスト | ソリューション系 | 操作性、価値理解 |
| データ分析 | プロダクト設計系 | 既存データから傾向確認 |
| エキスパートインタビュー | 戦略系 | 業界構造、技術トレンド |

## 検証結果の判定

| 判定 | 意味 | 対応アクション |
|:---:|------|--------------|
| 📗 支持 | 検証で仮説が支持された | VPC/リーンキャンバスに反映、プロダクト設計に活用 |
| 🔄 要修正 | 方向性は正しいが内容修正が必要 | 仮説を修正して再定義 |
| ❌ 棄却 | 検証で否定された | 方向転換。新たな仮説を立案 |
| 💡 未検証 | データ不足 | 追加検証の計画を立てる |

## アイデア発想時の注意点

仮説を立てる際、以下の4つの罠に注意する。

1. **アイデアソードファイト**: メンバー同士が自分のアイデアで斬り合い、最強のアイデアを決めようとする。建設的な議論にならない
2. **批判一辺倒**: ダメ出しばかりで、アイデアが育たない
3. **自己投影思考**: 自分の望みをユーザーに投影する。「自分が欲しいもの ≠ ユーザーが欲しいもの」
4. **結論を急ぐ**: 十分な検討をしないまま「これでいこう」と決めてしまう

**対策**: 仮説はあくまで「検証すべき推測」として扱い、正しい/間違いの判断はデータで行う。

## 価値の分類

仮説を評価する際、以下の2種類の価値を区別する。

- **大価値（構造的価値）**: これがないと次のステージに進めない。プロダクトの根幹に関わる
- **肉付け価値（継続的価値）**: ユーザー体験を向上させるが、なくてもプロダクトは成立する

> 検証の優先順位は「大価値に関する仮説 > 肉付け価値に関する仮説」。

## ステップ

1. **VPCからの仮説抽出**: VPCの各項目（Jobs/Pains/Gains/Pain Relievers/Gain Creators）を見直し、💡マークで仮説を洗い出す
2. **4段階深掘り**: 各仮説を「事実→分析→戦略→提案」で深掘りする
3. **カテゴリ分類とID付与**: 仮説をA〜Dのカテゴリに分類し、IDを振る
4. **確信度・優先度の評価**: 各仮説の確信度と優先度を評価し、検証の順序を決定
5. **検証ポイント設計**: 優先度の高い仮説から、検証方法・判定基準を設計
6. **検証実施後**: 検証結果マトリクスに結果を記録し、プロダクトへの示唆を抽出
