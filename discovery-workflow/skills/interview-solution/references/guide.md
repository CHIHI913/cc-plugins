# ソリューション検証インタビュー ガイド

## このガイドについて

プロダクトの具体的な機能・プロトタイプを実際のユーザーに触ってもらい、価値が伝わるか・行動変容（会員登録・エントリー等）に繋がるかを検証するための方法を解説する。

- テンプレート: [template.md](template.md)

## ソリューション検証インタビューとは

ペイン・ゲイン検証で確認された課題に対して、プロダクトのソリューションが実際に刺さるかを検証するプロセス。プロトタイプや開発環境を使って、ユーザーの反応を観察する。

**目的**: 「このソリューションでユーザーの行動が変わるか」を確認する
**インプット**: プロトタイプ or 開発環境 + ペイン・ゲイン検証結果
**アウトプット**: 検証結果 + 改善点 + ユーザビリティフィードバック

## ディスカバリーワークフローにおける位置づけ

```
ペイン・ゲイン検証インタビュー
        ↓
VPC更新（検証結果を反映）
        ↓
ソリューション設計
        ↓
 【ソリューション検証インタビュー】◀ ここ
    (プロトタイプを触ってもらう)
        ↓
 プロダクト改善・Go/No-Go判断
```

## ペイン・ゲイン検証インタビューとの違い

| 項目 | ペイン・ゲイン検証 | ソリューション検証 |
|------|------------------|------------------|
| 目的 | 課題の存在を確認する | 解決策が刺さるか確認する |
| 対象物 | 質問（仮説ベース） | プロトタイプ / 開発環境 |
| 方法 | 半構造化インタビュー | 思考発話法 + インタビュー |
| アウトプット | VPC更新 | 改善点 + Go/No-Go判断 |
| タイミング | Whyフェーズ（VPC作成後） | Whatフェーズ（プロトタイプ作成後） |

## プロトタイプの準備

ソリューション検証にはプロトタイプが必要。フィデリティ（忠実度）はプロダクトの段階に応じて選ぶ。

| 手法 | フィデリティ | メリット | デメリット |
|------|:---:|---------|----------|
| ペーパープロトタイプ | 低 | 最も早く作れる | インタラクションが限定的 |
| Figma/Adobe XD | 中 | クリック遷移まで再現可能 | 実データでの動作確認不可 |
| オズの魔法使い | 中〜高 | 実際のインタラクションに近い | 裏側で人が操作する必要がある |
| 開発環境（実装済み機能） | 高 | 実データ・実動作で検証可能 | 開発コストがかかる |

**注意**: プロトタイプの完成度が低すぎると「ここが動かない」等のUI問題に意見が集中し、本質的なフィードバックが得られない。一方で作り込みすぎると検証前にコストをかけすぎるリスクがある。

## 候補者の収集

### 必要な人数

> ニールセンの法則: 5名で全体インサイトの80%以上を獲得できる

**推奨**: 1セグメントあたり5名程度。ペイン・ゲイン検証で話を聞いた人に再度依頼できると、前提の理解が深い状態で検証できる。

### 候補者の条件

- ペイン・ゲイン検証で確認された課題を持っている人が理想
- ただし、課題感のない人にも検証することで「前提が成り立たない場合の反応」を把握できる（参考情報として有用）

## 検証の構造

ソリューション検証は以下の3層で設計する:

### 1. 前提検証

ソリューションが刺さる前提条件（課題感）が存在するか確認する。前提が成り立たない場合、ソリューションの検証結果は参考情報にとどまる。

**判定基準の例:**
- **顕在的**: 課題を感じており、何かしら行動した/しようとしている
- **潜在的**: 課題への不安はあるが、対策は具体的にしていない
- **なし**: 課題を感じていない

### 2. コンバージョン検証

ソリューションを見せた/触ってもらった結果、ユーザーの行動が変わるかを確認する。検証ポイントはファネルの各ステップごとに設計する。

例:
- 広告 → 会員登録（フック検証）
- 会員登録後 → エントリー（コンバージョン検証）
- 無料版 → 有料版（アップセル検証）

### 3. ユーザビリティテスト

操作中のわからなかったもの・迷った箇所を洗い出す。思考発話法で観察する。

## スクリプト設計

### 基本構造と時間配分

| セクション | 時間 | 目的 |
|-----------|------|------|
| Q0: 導入・アイスブレイク | 3分 | 心理的安全性の確保、録音許可 |
| Q1: 前提検証 | 7分 | 課題感の有無を判定 |
| Q2: コンバージョン検証① | 5分 | ファネルステップ1（広告/LPの反応） |
| Q3: コンバージョン検証② | 15分 | ファネルステップ2（プロトタイプ操作、思考発話法） |
| Q4: 価値の言語化 | 3分 | ユーザー自身の言葉で価値を表現 |
| Q5: ユーザビリティテスト | 5分 | 操作中の不明点・改善点 |
| Q6: クロージング | 5分 | 率直な感想・謝礼 |
| **合計** | **約43分** | |

### 質問設計の原則

**オープン質問を使う**
- ❌「この機能を利用しますか？」（Yes/No、開発者を前に「いいえ」と言いづらい）
- ⭕「どんなときに使いたくなりそうですか？」（5W1H）

**利用シーンを聞く**
- ❌「このプロダクトはよいと思いますか？」（評価を求めると好意的になる）
- ⭕「このプロダクトをどんなシーンで利用すると思いますか？」

**引き算で優先度を引き出す**
- ❌「良かった機能はどれですか？」（好意的回答に誘導）
- ⭕「この中で1つ機能を外すならどれですか？」

**紹介依頼で価値を言語化させる**
- 「このプロダクトを使ってくれそうな方を紹介してくれませんか？」
- → どういうユーザーがどんなシーンで使うか、どんな価値を感じたかを参加者自身の言葉で説明してくれる

## 思考発話法（Think Aloud）

ユーザーに操作しながら思ったことをすべて口に出してもらう方法。ソリューション検証の核となるテクニック。

**導入の言い方例:**
「操作しながら、思ったことをすべて口に出していただけると助かります。『ここがわかりにくい』『これは良さそう』『ここの意味がわからない』など、なんでも口に出していただけると参考になります。」

**観察ポイント:**

| 観察項目 | 記録すべきこと |
|----------|--------------|
| 最初に目がいった場所 | ファーストインプレッションの確認 |
| 迷った・止まった場所 | UXの改善ポイント |
| 反応が良かった場所 | 価値が伝わっている箇所 |
| 操作の自然さ | UIの直感性 |
| 発言メモ | 印象的な発言を原文のまま記録 |

**沈黙が続いたら:**
「今何を考えていますか？」「どこを見ていますか？」と促す。

## インタビュー実施

### 謝礼について

| 謝礼あり | 謝礼なし |
|---------|---------|
| 真剣に回答してくれる | インセンティブが働かない |
| 役に立とうとして好意的発言をすることも | 質の高い答えを得られないことも |

**注意**: ソリューション検証は特に好意的バイアスが入りやすい（開発者の目の前で「いらない」とは言いづらい）。「批判的な意見も歓迎」「微妙・いらないという意見も大歓迎」と冒頭で繰り返し伝える。

### 実施時の注意

- **録音**: 必ず許可を得て録音する。思考発話法の発言は後から振り返りが必須
- **画面録画**: スマホ操作の場合は画面共有+録画。操作の迷いを後から分析できる
- **メモ**: リアルタイムで観察ポイントをメモ。操作を邪魔しないよう別の人が記録するのが理想
- **チーム参加**: 開発メンバーは別室でオンライン視聴 or 録画視聴。大人数で押しかけると参加者が萎縮する
- **非言語情報への注目**: 表情の曇り、ため息、首をかしげる等の非言語反応はUX改善の重要な手がかり

### 避けるべきこと

- プロトタイプの操作方法を先に説明しすぎる（ユーザーが自力で理解できるかも検証ポイント）
- ユーザーが迷っているときに「ここを押してください」と誘導する
- 「このプロダクトは素敵なものに違いない」という姿勢が伝わること
- 操作中の発言に対して「そうですよね」「いいですね」と肯定反応を返しすぎる

### 記録のポイント

- **事実と解釈を分ける**: ユーザーの発言・行動（事実）と自分の解釈を区別して記録
- **印象的な発言は原文のまま**: 分析やチーム共有で使える
- **操作の時系列を記録**: 「最初に○○を見た→次に△△をタップ→□□で迷った」

## 検証結果の判定

### 判定基準の例

| 判定 | 基準の目安 | 対応 |
|:---:|---------|------|
| ✅ 検証成功 | 過半数が自発的に行動変容（登録・エントリー等の意向を示す） | Go。改善点を反映して開発を進める |
| △ 部分的 | 価値は理解されるが行動変容に至らない | 改善後に再検証。フック/導線の見直し |
| ❌ 検証失敗 | 課題感が確認できない、または解決策として認識されない | ピボットまたはソリューションの再設計 |

### ソリューションが刺さらなかったら

> 「往々にして、ソリューション検証を通して残念ながらプロダクトの方向性が間違っていたことが判明する。リリース前に間違いに気づけたことを喜ぼう。」

**確認すべきこと:**
- そもそも課題感（前提）が弱かった？
- 課題はあるがソリューションの方向が違った？
- ソリューションの方向は合っているがUX/導線が悪い？
- ターゲットが違った？（課題感のある別のセグメントがいるのでは）

前提検証・コンバージョン検証・ユーザビリティテストのどの層で失敗したかによって、次のアクションが変わる。

## 実践から得られた学び

### プロトタイプ準備のポイント

- ダミーデータと実データが混在すると混乱を招く。可能な限り対象者自身の情報で埋める
- ロック/アンロック等の導線は自明に見えても伝わらないことがある。導線設計は検証の重要ポイント
- スマホ操作の場合、画面共有によるボタンの見えにくさ等の環境要因を考慮する

### インタビュー設計のポイント

- 「この機能を使えそうな人はどんな人か？その人にどう紹介するか？」が最も本質的な質問。ユーザーが価値を自分の言葉で語れるかが成功の指標
- 率直な感想を最後に聞く。友人関係等のラポールがあれば正直なフィードバックが得られる
- 全体フロー（登録→面談→完成→エントリーまでのリードタイム）の可視化がないと不安を感じるユーザーがいる
